# Пансионат «Солнышко» и УринаТех

Основной сайт — пансионат «Солнышко»: направления здравницы, проживание,
питание и справочные бланки путёвок. Из раздела уринотерапии доступен полный сайт производителя
«УринаТех» с каталогом, архивом партий и донорской программой.

Проект — сайт-реставрация легендарного ресурса `urina-ru.narod.ru`
(Московский Институт Обогащения Урины, 2002). Концепция, ассортимент
и правовая позиция оригинала сохранены.

> Имеются противопоказания. Необходима консультация специалиста. 18+

Репозиторий: [enikey87/mu-hospital](https://github.com/enikey87/mu-hospital).
Сайт: [enikey87.github.io/mu-hospital](https://enikey87.github.io/mu-hospital/).

## Навигация

- `/` и `#/` — главная пансионата; `#/solnyshko` сохранён как старый адрес.
- `#/solnyshko/morozko` — каловая криотерапия «Морозко», холодовые партии и отдельный учёт разморозки.
- `#/solnyshko/golden-reserve` — капельная уринотерапия «Золотой резерв», три донорские программы и именная выписка.
- `#/solnyshko/station` — уринотерапия; остальные направления имеют собственные страницы.
- `#/urinatech` — производитель; `#/urinatech?section=products` — его каталог.
- `#/urinatech?section=urinatorium` — первый уринаторий, изолят отборной мочи и аппарат «Солнышко-У» с семейной комплектацией.
- `#/urinatech?section=ug9` — предложение анального кольца УГ-9: девять свойств, удержание до 12 атм и комплект замены.
- `#/solnyshko/franchise` — франшиза калофореза с аппаратом «Калофорез-Кедр М2», условия открытия и локальный расчёт комплектации.
- Старые якоря производителя, например `#products` и `#company`, сохраняют назначение.

Решение и таблица маршрутов: [структура сайтов](docs/design/site-hierarchy.md).

У производителя собственный дизайн [«Промышленный монумент»](docs/design/urinatech-monument.md): графит, красный акцент, локальный Oswald и фотографии продукции. Здравница сохраняет бело-синий стиль; темы разделены контейнерами `.ut` и `.sol`.

Позиционирование уринатория и происхождение фотографии аппарата: [«Солнышко-У»](docs/design/urinatorium.md).

Новые программы и происхождение графики: [«Морозко» и «Золотой резерв»](docs/design/morozko-golden-reserve.md).


## Публикация

### Обычный стенд с nginx

Сайт статический: на сервер выкладывается содержимое `dist/`. Node.js нужен
только для сборки; backend, база данных, переменные окружения и процесс Node.js
на стенде не требуются. Состояние MobX хранится в браузере; серверного сохранения
данных в проекте нет.

Используйте Node.js 22 (как в GitHub Actions) или 24 и npm:

```bash
npm ci
npm test
npm run build -- --base=/
```

Параметр `--base=/` обязателен для размещения в корне домена: обычный
`npm run build` создаёт ссылки с префиксом `/mu-hospital/` для GitHub Pages.
CLI-параметр переопределяет `base` в `vite.config.ts`, сохраняя production-режим.
Для локального предпросмотра этой сборки: `npm run preview -- --base=/`.

Пример конфигурации: [deploy/nginx.conf](deploy/nginx.conf). Замените
`hospital.example.com` на домен стенда; `root` должен указывать на каталог,
в котором непосредственно лежит собранный `index.html`.

После доставки `dist/` и конфигурации на сервер (команды выполняются на сервере
из каталога доставленного проекта; nginx уже установлен):

```bash
sudo install -d -m 755 /var/www/mu-hospital
sudo cp -a dist/. /var/www/mu-hospital/
sudo chmod -R a+rX /var/www/mu-hospital
sudo install -m 644 deploy/nginx.conf /etc/nginx/conf.d/mu-hospital.conf
sudo nginx -t && sudo systemctl reload nginx
curl -I -H 'Host: hospital.example.com' http://127.0.0.1/
```

Конфигурация должна подключаться внутри `http {}` основного nginx.conf.
На существующем стенде используйте отдельный `server_name` или перенесите
директивы в его виртуальный хост. Пример обслуживает HTTP; при использовании
HTTPS подключите сертификат в виртуальном хосте или используйте TLS-терминацию
стенда. Новые сборки выкладывайте в тот же `root`; nginx перезапускать не нужно.
Старые хешированные assets можно оставить на время для уже открытых вкладок.

Маршрутизация использует `#/…`, например `/#/urinatech`: nginx получает только
путь `/`. Поэтому fallback на `index.html` для неизвестных путей не нужен:
отсутствующие файлы и пути возвращают HTTP 404. `public/404.html` предназначен
для GitHub Pages и перенаправляет на `/mu-hospital/`; пример nginx блокирует
его выдачу и использует стандартную страницу ошибки nginx.

`robots.txt`, `sitemap.xml` и контрактные тесты пока закреплены за доменом
GitHub Pages. Для публичного домена потребуется отдельная настройка метаданных
сборки: автоматическая подстановка домена стенда пока не реализована.
В `index.html` также есть загрузка шрифтов с Google Fonts; при недоступности
сервиса используются резервные шрифты.

### Архив из GitHub Actions и выкладка Ansible

Workflow [Build nginx archive](.github/workflows/build-archive.yml) запускается
на push в `main` и `feature/**`, pull request и вручную через Actions → Run workflow.
Он проверяет playbook, запускает тесты сайта, собирает сайт с `--base=/`
и для push/ручного запуска сохраняет artifact `mu-hospital-COMMIT_SHA`.
PR проверяют сборку без загрузки артефакта. После проверки загруженного архива
CI оставляет **три последних дистрибутива суммарно по всем веткам**, остальные
дистрибутивы удаляет; артефакты других типов, в том числе GitHub Pages, не трогает.
Дополнительно действует срок хранения 90 дней (в пределах лимита репозитория).
Внутри — `mu-hospital-COMMIT_SHA.tar.gz` и файл
`.tar.gz.sha256`. В архиве лежит содержимое `dist/`, включая `version.txt`
с полным SHA коммита.

Сервер пока не подключён: job `deploy-placeholder` скачивает дистрибутив,
проверяет SHA256 и наличие `index.html`, затем пишет в сводку, что деплой —
заглушка. SSH и Ansible на реальном сервере из CI не запускаются.
Playbook ниже подготовлен для будущего сервера и сейчас тестируется локально.

Архив можно скачать в интерфейсе завершённого workflow или через GitHub CLI
(замените `RUN_ID` и `COMMIT_SHA` значениями выбранной сборки):

```bash
gh run list --repo enikey87/mu-hospital --workflow build-archive.yml --branch main --status success
gh run download RUN_ID --repo enikey87/mu-hospital \
  --name mu-hospital-COMMIT_SHA --dir /tmp/mu-hospital-artifact
cd /tmp/mu-hospital-artifact
sha256sum --check *.sha256
```

На управляющей машине нужны Ansible (playbook проверен с ansible-core 2.20.1),
SSH-доступ и sudo на сервере. На сервере — Python 3, GNU tar и gzip; nginx
должен быть установлен и настроен по [deploy/nginx.conf](deploy/nginx.conf)
с доменом стенда. Node.js и доступ сервера к GitHub не требуются.

В этом варианте nginx смотрит на симлинк `/var/www/mu-hospital`, которым
управляет Ansible. Не создавайте этот путь командой `mkdir` из инструкции
ручной выкладки выше. Если там уже лежит обычный каталог, сначала перенесите
его в резервное место в окно обслуживания: playbook откажется его заменять.

Из корня репозитория:

```bash
cp deploy/inventory.example.ini deploy/inventory.ini
# Укажите в deploy/inventory.ini адрес сервера и SSH-пользователя.
ansible-playbook -i deploy/inventory.ini deploy/deploy.yml \
  -e archive_path=/tmp/mu-hospital-artifact/mu-hospital-COMMIT_SHA.tar.gz
```

`archive_path` — абсолютный путь на управляющей машине. При необходимости
добавьте `--ask-become-pass`; другой document root задаётся через
`-e site_root=/var/www/another-site` и соответствующий `root` nginx.

Playbook распаковывает архив в `/var/www/mu-hospital-releases/<SHA256>/`,
проверяет `index.html` и атомарно переключает симлинк `/var/www/mu-hospital`.
Повторная выкладка того же архива не меняет сервер. Настройку nginx и TLS
выполняют один раз отдельно; при переключении релизов reload не нужен.
После выкладки проверьте главную и `https://ДОМЕН/version.txt`: он должен
вернуть SHA выбранной сборки. Playbook проверяет файлы до переключения;
доступность сайта по HTTP проверяется отдельно.

**Откат:** запустите ту же команду с `archive_path` предыдущего архива.
Старые каталоги релизов автоматически не удаляются. Для долгосрочного отката
сохраните нужные архивы вне Actions до истечения срока хранения.
При переключении уже открытая вкладка может запросить ресурс старого релиза,
которого нет в новом; в этом случае нужно обновить страницу.

Проверка механизма выкладки без SSH и sudo (только временный каталог):

```bash
python3 tools/test-deploy.py
```

Покрыты первая выкладка, повторный запуск без изменений, обновление, отказ
на архив без `index.html` с сохранением текущего сайта, откат и защита
существующего обычного каталога от замены.

### GitHub Pages

Публикация выполняется автоматически через GitHub Actions при пуше в `main`:
тесты, сборка и деплой на GitHub Pages. В pull request выполняются тесты
и сборка без публикации. Настройки Pages: Source → GitHub Actions.
